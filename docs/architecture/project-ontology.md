# 프로젝트 오너 운영 온톨로지

## 목적

SFH의 기획·코드·데이터·테스트를 문서 목록이 아니라 **판단 가능한 객체와 관계**로 연결합니다. 최종 판단 주체는 기획자나 AI 개발자가 아니라 프로젝트 오너입니다. 이 구현은 Palantir Foundry 제품을 복제하거나 도입한 것이 아니라, 공식 온톨로지 개념의 객체·관계·행동·인터페이스·권한을 SFH 위키 규모에 맞춰 적용한 것입니다. [공식 Ontology 개요](https://www.palantir.com/docs/foundry/ontology/overview)

| 역할 | 책임 | 최종 확정 |
|---|---|---|
| 프로젝트 오너 | 범위·우선순위·수락·출시 판단 | 가능 |
| 기획자 | 플레이 의도·수치 후보·예외·검수 근거 제출 | 불가 |
| 개발자 | 구현 영향·회귀 위험·E2E·배포 근거 제출 | 불가 |

## 운영 모델

### 의미 계층

| 구성 | SFH 객체 | 질문 |
|---|---|---|
| 객체 유형 | 원칙·결정·위험·작업·모듈·문서·문서 묶음·원본·역할 | 무엇을 추적하는가? |
| 속성 | 상태·확실성·요약·수락 조건·다음 행동·경로 | 지금 어떤 상태인가? |
| 관계 | 판단·근거·구현·검증·설정·영향·차단·의존 | 왜 연결됐으며 무엇에 영향을 주는가? |
| 인터페이스 | 오너 판단 가능·원본 추적 가능·검증 가능 | 객체가 반드시 만족할 공통 계약은 무엇인가? |

### 행동 계층

| 순서 | 행동 유형 | 실행 주체 | 가드 |
|---:|---|---|---|
| 1 | 기획 근거 제출 | 기획자 | 제안은 자동 확정되지 않음 |
| 2 | 범위·우선순위·수락 판단 | 프로젝트 오너 | 오너만 최종 상태를 결정 |
| 3 | 모듈 구현 | 개발자 | 승인된 수락 조건과 모듈 경계 필요 |
| 4 | 플레이어 인식 검증 | 개발자·CI | 실패 시 수락·병합 금지 |
| 5 | 병합·배포 | 프로젝트 오너·CI | 필수 검사 성공 산출물만 배포 |

현재 콘솔은 이 행동을 **설명하고 계보를 보여주는 읽기 전용 화면**입니다. 위키에서 자동 승인하거나 코드·데이터·배포·과금 설정을 변경하지 않습니다.

## 단일 원본과 계보

### 판단 폐루프

```text
Notion 의도·상태 ─┐
Google Sheet 후보 ─┼→ 오너 판단 → Git 구현 → E2E 검증 → CI·배포
확정 CSV 런타임 ──┘       ↑                              │
                          └──────── 결과·위험 환류 ──────┘
```

| 원본 시스템 | 소유 정보 | 콘솔의 역할 |
|---|---|---|
| Notion | 기획 의도·확정/임시/보류 후보 | 판단 근거 링크 |
| Google Sheet | 목록형 수치 후보와 설명 | 후보 데이터 링크 |
| 저장소 CSV | 빌드가 사용하는 확정 런타임 값 | 설정 계보 |
| Git | 코드·문서·레지스트리 이력 | 구현 원본 |
| 플레이어 인식 E2E | 입력→상태 변화→결과→다음 행동 | 수락 근거 |
| CI·Cloudflare | PR 검사·Web/Windows 동등 산출물·배포 | 출시 근거 |

위키는 원본의 값을 복제해 새 진실로 만들지 않습니다. `owner-decision-registry.json`이 수동 판단 대상·관계·행동 계약을 선언하고, `generate_project_ontology.py`가 코드 모듈 지도·전체 문서 지도·현행 마일스톤 표를 결합해 보호된 `project-ontology.json`을 생성합니다.

### 자동 수집 범위

| 입력 원본 | 생성되는 객체·관계 | 수동 중복 작성 금지 |
|---|---|---|
| `knowledge-map.json` | 종합→대분류→중분류 `collection`, 문서의 `part_of` 관계 | 문서 소속 관계 |
| `current-milestone-workline.md` | `BASE-*`, `P*-*` 행별 `work_item`, 오너·Git·E2E·Notion 계보 | 마일스톤 작업 객체 |
| `code-module-map.json` | 코드 `module`, 위키 설명 문서 관계 | 모듈 객체와 문서 연결 |
| `notion-source-snapshot.json` | Notion 관측 시각·revision·해시 | 스냅샷 최신성 상태 |
| `notion-tracker-snapshot.json` | 기능 트래커 전체 행·별도 해시·관측 상태 | 기획 상태와 수락 기준 |

### 최신 원본 대조 계약 · 2026-09-07

GDD 수집기는 선택한 원본의 본문 하위 블록만 읽고 상위 페이지 메타데이터는 제외합니다. 트래커 수집기는 전체 결과임이 확인되지 않거나 행이 누락·중복되면 실패합니다. 두 수집기는 노션을 수정하지 않습니다.

`notion-code-audit.json`은 행별 코드·기존 검사 근거·판정·다음 작업을 기록한 수동 검토 결과입니다. `check_notion_audit.py`는 두 원본 해시, 전체 행 대응, 기획 상태 보존, 근거 경로와 산정식을 검사하고 대조 문서를 생성합니다. 최초 66행·123/170에서 N26-03A/B 근거 1행을 반영해 124.5/170으로 갱신했습니다. 원본 갱신 때 수동 재대조 없이 해시만 바꾸지 않습니다. 근거 파일 존재는 최신 요구의 실제 E2E 통과를 의미하지 않습니다.

N26 결정·작업 객체는 아직 공식 Phase가 아니므로 레지스트리에서 선행 결정·작업 의존성을 선언합니다. 기존 P1~P10의 완료 이력을 삭제하거나 기획자의 미구현 태그로 초기화하지 않습니다. 상세 충돌은 [오너 판단표](../design/master-gdd-alignment.md#owner-conflicts)를 사용합니다.

Google Sheet는 라이브 revision을 저장소가 아직 자동 관측하지 못하므로 항상 **원본 확인 필요**로 표시합니다. 목록·밸런스 작업 직전에 대상 탭을 읽고 확정 CSV 해시와 함께 검증한 뒤에만 구현 근거로 사용합니다. Notion 스냅샷은 관측 후 7일이 지나면 콘솔에서 **갱신 확인 필요**로 바뀝니다. 이 경고는 원본을 자동 수정하거나 확정하지 않습니다.

## 개발자 콘솔 · 개요에서 근거로 좁히는 다섯 화면

1. **작업 개요 (기본):** 현재 작업의 다음 행동, 선행 조건, 원본 확인 경고만 먼저 봅니다. 상태 집계는 등록 객체 수이며 게임 진행률이 아닙니다.
2. **판단 대기열:** 결정·위험·작업·원칙을 상태와 수락 조건순으로 확인합니다.
3. **객체 탐색:** 판단 객체뿐 아니라 코드 모듈·문서·원본 시스템·역할까지 검색합니다. 전체 객체를 6개씩 넘겨 보며 선택한 객체의 상태·수락 조건·다음 행동을 옆 검사 패널에서 읽습니다.
4. **관계·계보:** 선택 객체의 원본·선행 조건과 구현·검증·영향을 양방향으로 추적합니다.
5. **행동·관측:** 깨진 관계·고립 문서·원본 최신성을 먼저 보고, 행동 계약은 펼쳐서 확인합니다.

객체나 관계가 문서·모듈에 연결되면 해당 내부 페이지로 바로 이동합니다. 검색·유형·상태·목록 페이지는 같은 화면 안에서 탭과 객체를 바꿔도 유지됩니다. 검색 결과가 없으면 이전 객체의 검사 패널도 비워 오인하지 않게 합니다. 새로고침은 URL의 `view`·`decision`을 복원하며 검색 필터는 초기화합니다.

탭은 좌우 화살표·Home·End로 이동하며 선택 시 활성 패널을 접근성 속성으로 연결합니다. 좁은 화면은 목록 아래 검사 패널로 재배치하고 선택 시 패널에 포커스를 보냅니다. 코드 노드맵과 긴 운영 안내는 기본 접음이며 코드 JSON은 처음 펼칠 때만 요청합니다. 전체 문서를 삭제하거나 권한을 완화한 것이 아닙니다.

`data-focus-object`는 현재 작업 개요의 객체 ID만 지정하는 표시 계약입니다. 작업 변경 시 기존 레지스트리의 유효 ID로 갱신하고, 상태·다음 행동·근거는 JSON 원본에서 읽습니다. 지정 ID가 없으면 판단 대기 객체로 안전하게 대체합니다. UI에 새 업무 상태나 별도 진행률 저장소를 만들지 않습니다.

## 권한 경계

- 공개 사용자는 홈·로그인·표현 자산만 접근합니다.
- 기획자는 기획자 작업실과 전체 내부 문서를 읽지만 개발자 작업실·온톨로지 원본과 생성 JSON은 열 수 없습니다.
- 개발자는 개발자 작업실, 운영 온톨로지, 전체 내부 문서를 읽습니다.
- 익명 요청은 내부 HTML·검색 색인·사이트맵·JSON 본문을 받기 전에 로그인으로 이동합니다.
- 인증된 응답은 `private, no-store`로 전달합니다.

## 변경 절차

1. 신규 판단 대상에 고유 ID, 상태, 확실성, 프로젝트 오너, 수락 조건, 다음 행동을 기록합니다.
2. 관계는 `document:<경로>`, `module:<모듈>`, `source:<원본>` 같은 실제 객체 ID를 사용합니다.
3. `python scripts/generate_project_ontology.py`로 산출물을 갱신합니다.
4. 생성 검사가 인터페이스 필수 속성, 행동 주체, 생명 주기 원본, 중복 ID, 깨진 관계, 고립 문서, 자동 마일스톤 계보와 원본 최신성 메타데이터를 검사합니다.
5. 역할 인증 E2E가 익명·기획자·개발자별 경계를 검증합니다.
6. 실제 렌더와 반응형 E2E, MkDocs strict 빌드, PR 필수 검사 뒤에만 배포합니다.

## 완결 기준과 중단 조건

이 구조에서 ‘완결’은 객체 수가 많은 상태가 아니라 다음 폐루프가 끊기지 않는 상태입니다.

- 판단 객체마다 프로젝트 오너·현재 상태·수락 조건·다음 행동이 있음
- 근거→판단→구현→검증→배포 중 존재하는 단계가 관계로 추적됨
- 깨진 관계와 오너 없는 판단 객체가 0임
- 공개·기획·개발 권한이 서버에서 차단됨
- 원본과 파생 뷰가 충돌하면 원본과 검증 결과가 우선함

수동 상태가 원본보다 자주 뒤처지거나, 같은 판단을 여러 곳에 중복 작성하거나, 그래프 유지가 게임 개발을 침범하거나, 근거 없이 `구현·검증됨`이 표시되면 객체 확장을 멈추고 자동 수집과 검증부터 보강합니다.
